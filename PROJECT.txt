RouteVela - Product specification and construction guide
Baseline: revised preparation design, 2026-10-13
Repository: https://github.com/mehrangtr/RouteVela
This file specifies intended behavior. STATE.json and test evidence describe actual progress.

1) Product requirements

R01. Deliver a real personal connection, free to end users, with simple installation and a polished interface.
R02. The creator's mandatory external expense is limited to registering/renewing at most two domains. No mandatory VPS, paid plan, API or central service.
R03. Each installation and its data belong to its operator. An operator may serve authorized subscription recipients; each recipient need not own a Cloudflare account.
R04. A panel or config generator without a working connection does not satisfy the goal. Do not silently substitute a paid VPS.
R05. Preserve Persian/English UI, RTL, mobile usability, accessibility, light/dark/system themes and simple/expert modes.
R06. Modular implementation, understandable diagnostics, interruption recovery and tests during construction are required.
R07. Keep reports short and authorities singular. Publish only completed phases unless the owner explicitly requests earlier publication.
R08. Admin, subscription and connection credentials are independent. Configuration rollback or backup restore must never undo revocation.
R09. Do not log traffic contents or browsing history. Diagnostic exports are local, redacted and sent only by user action.
R10. Require real validation, encrypted backups, tested recovery and inspectable releases.
R11. No quota evasion, account multiplication, Worker renewal tricks or mandatory unknown egress.
R12. Learning from ideas does not grant permission to copy code. Review each dependency's license and provenance.
R13. Protect ownership and installations without spyware, backdoors, central kill switches or paid activation locks.
R14. Reduce repeated context and work without sacrificing security, quality or meaningful tests.
R15. All repository prose, comments, identifiers and commit messages use English. Owner-facing chat remains Persian. Future Persian UI resources use escaped Unicode in dedicated localization files; test the decoded text and RTL behavior.
R16. Optional bootstrap assistance helps users reach installation prerequisites on filtered networks; it must not become a mandatory relay, recurring cost or unverified proxy distribution service.
R17. Support Windows and Linux for desktop use and development. The service runs in the permitted cloud runtime; users access the web interface and a compatible client on their own OS. Core logic, developer commands and offline help must be portable. Verify actual OS/client/browser versions before claiming support.

2) Feasibility and delivery gates

Preparation and independent local development can proceed. A permitted, genuinely free public connection remains unproven.
The dated Cloudflare findings in docs/SOURCES.json identify the written-permission exception and VPN/similar-proxy restriction in Self-Serve 2.2.1. Recheck applicable terms before deployment.
Pages is not a permission exception. Pages Functions share Workers resources; another hostname does not create independent permission, capacity or egress.
Publishing source to GitHub is distinct from deploying a service. No provider message or permission is implied by repository publication.
Keep sensitive permission documents private; record only status and a non-sensitive evidence reference.
A successful experiment, OAuth consent, disclaimer or local approval flag cannot establish provider permission.

During P01, review capabilities, free-egress candidates and existing permission evidence alongside local foundation work. P01.05 records the checkpoint; P02.03 revalidates before live experiments.
Unresolved external gates do not prevent completing tested local P01 work or controlled local P02 parsers/streams. They prevent live Cloudflare VPN deployment, P02 closure and P03+ product expansion.
At the blocked live step, finish useful independent work and report the specific missing prerequisite. Changed product goals or costs need an owner decision; routine local tasks do not need repeated confirmation.
Do not grow a large UI or implement optional features while the critical connection path remains unproven.

3) Core release behavior

Installation and ownership:
- Use the official installation flow when runtime and permission prerequisites are ready; the preparation skeleton has no active deploy button.
- Explain access and resources before authorization. Resume interrupted installation without duplicate resources.
- Track installation-owned resources and support selective removal; preserve unrelated resources and require a clear decision before deleting data.
- The operator account is independent of the creator. RouteVela never collects or stores a Cloudflare account password.
- Provide Windows PowerShell and Linux shell instructions using the same portable npm commands for development. End users do not need Node.js merely to use the future web panel.
- Provide downloadable offline setup/recovery help and use the operator's existing trusted connection for initial account access.

Connection:
- First evaluate one small VLESS-over-WebSocket/TLS path for simplicity and compatibility, without claiming it is fastest.
- Separate protocol, transport, provider and client format. WebSocket is the client-to-edge transport, not the only destination protocol.
- Stream with bounded memory, backpressure, cancellation, timeouts, cleanup and bounded retries.
- Direct outbound connectivity must be permitted and supported. Any necessary relay needs known provenance, applicable permission and genuinely zero required cost.
- Do not promise UDP, gaming, calls, WireGuard, Hysteria2 or universal destination reachability without demonstrated capabilities.
- Even feasibility prototypes need authentication, appropriate target restrictions, verified TLS and resource bounds. No public unauthenticated relay.

Users, profiles and subscriptions:
- One administrative owner in v1; no multi-tenant organization or complex RBAC.
- Stable user identity, enable/disable, expiry and independently rotatable/revocable credentials.
- Links, QR and client-specific import/update help. Complete one client flow first, then support both pinned sing-box and Mihomo families before P03 closes.
- The desktop compatibility matrix must include Windows and Linux, with actual client/core/OS versions. Download selection, paths, process cleanup and any later local helper are OS-specific adapter concerns; no Bash, WSL, sudo or administrator access is a default prerequisite for both platforms.
- A small profile library records an opaque ID, name, optional group, source, revision, protocol/transport and credential reference; credentials are not copied into display metadata.
- Record parse/import/connect/update outcomes separately with tested client/core version, observation time and origin, and a stable error code. Unsupported, not_run and stale results remain explicit.
- Imported profiles are untrusted: enforce size/count limits, schema/semantic/capability validation, safe text rendering and supported fields. A paste/import does not trigger a network fetch or activate a profile.
- Do not silently drop incompatible settings or convert a profile into a format that cannot preserve supported semantics.
- Profile history and backup cannot preserve an obsolete credential as valid. Reconcile through the independent credential lifecycle.

Identity and recovery:
- Bootstrap a unique administrator; no public default password, shared UUID/password or credential in README.
- Choose one main login method with maintained libraries and tested recovery after a CPU/UX spike: passkey or a strong password with TOTP.
- Secure sessions, applicable CSRF defenses, bounded login attempts and complete separation of credential purposes.
- Enforce expiry and revocation on the connection path. Measure propagation bounds and policy for already-open sessions.
- Configuration lifecycle: draft -> validate -> preview -> atomic activate -> known-good -> safe rollback.
- Rollback changes configuration, never the authoritative revocation generation.
- Encrypt backups with an independent recovery secret. Test wrong passwords, corruption, fresh-install restore and failed migrations.
- If revocation freshness cannot be established during restore, rotate/invalidate affected credentials before reconnecting.
- Record only allowlisted administrative security events with bounded retention, not traffic or raw authentication material.

Interface and diagnostics:
- Consistent typography, spacing, restrained color and motion; mobile-first, keyboard-accessible and correct RTL with isolated technical identifiers.
- Essential screens: status, users, subscriptions/profiles, settings, backup/recovery, installation and diagnostics.
- Keep common actions short and loading/empty/error states clear. Simple mode exposes safe essentials; expert mode adds supported network controls.
- A bounded config playground: paste -> validate -> explain incompatible fields -> preview. Conversion and activation are separate explicit actions.
- Structured editing initially covers supported fields only. Reuse validator/compiler contracts instead of a universal network-rule editor.
- Errors carry a stable RV-MODULE-NNN code, component, stage, retryability and safe corrective action. A code identifies an observed failure class, not an unmeasured root cause.
- Public liveness is minimal; detailed readiness is admin-only. End-user connectivity must be observed from the user's network.
- Show last successful observation separately from current state. Expired observations become unknown/stale; server health is not a user's live connection.
- Stage diagnostics distinguish subscription retrieval, validation/import, endpoint reachability and end-to-end egress. DNS/TLS root causes remain unknown when unobservable.
- Browser HTTPS/WS checks are limited by CORS and browser APIs. Raw DNS, arbitrary SNI/Host, TCP and CDN scanning require an appropriate local client.
- Diagnostic exports use an allowlist, local preview and explicit send. Exclude secrets, full subscription URLs, cookies, payloads and browsing destinations.
- Document stored fields, purposes, readers, retention and deletion. Minimal app storage does not hide metadata from the provider.
- Quota estimates cite dated sources and distinguish estimates from measurements; user count alone cannot predict usage.

Release quality:
- Add tests with each module; small fixtures, pinned dependencies and provenance review from the first dependency.
- Maintain a small real compatibility matrix from the first supported client. CLI parsing is not mobile GUI import or real connection evidence.
- Verify artifacts and record dependency inventory, SBOM and release signatures for public releases.
- Claim reproducible builds only after demonstration; a lockfile alone is insufficient.
- At most two domains distribute the site, help, installation and known-good releases. They are not independent network exits.

4) Optional work after a stable core

- Multiple verified profiles and native client fallback/url-test with bounded probes; do not build a replacement VPN client.
- Local measurements, operator profiles and deterministic explainable advice, without a paid AI API.
- Bound profile count, bytes, concurrency, duration and retries; support cancellation and stale-result handling. Prefer successful connectivity over lowest ping.
- Fragment, Mux, noises, DNS and placement tuning requires pinned capability checks and controlled A/B evidence. Never inject these into every output by default.
- A subscription cannot run arbitrary JavaScript in every client. Switching routes does not migrate an existing TCP session automatically.
- No insecure direct route, disabled TLS verification or guaranteed always-on promise in default fallback.
- More protocols and visual routing require demonstrated user need.

Optional bootstrap access assistant (staged, not a core-release dependency):
- P06: offline setup/recovery help, using a trusted existing connection and resuming setup. Help must be obtainable before RouteVela connectivity exists.
- P09.05: evaluate a small dated catalog of reviewed tools/providers and optional local integration. No tool, permission, free quota or capacity is assumed available today.
- Integrate only services with known operator/provenance, compatible redistribution terms, a credible zero-cost budget and tested target-network access. Exclude unknown public subscription harvesting.
- A browser page cannot set a device proxy or reliably enforce a destination/byte quota. A scoped helper needs explicit OS/client integration and a trusted enforcement point; reject unsuitable maintenance or cost.
- For a limited-access offer, measure/enforce session duration, bytes, concurrency and required installation destinations using supported provider/helper controls. Recheck redirects and authentication dependencies; a static Cloudflare-only hostname list is insufficient.
- Keep end-to-end TLS verification. No custom root CA, login interception, password capture or certificate bypass. Reachability does not prove successful account creation or challenge completion.
- If justified, distribute an authenticated versioned catalog manifest with expiry, provenance, removal/revocation metadata and bounded size. Fetch on user action or a bounded TTL with backoff; polling every few minutes is not a default.
- An authentic manifest does not prove endpoints trustworthy or healthy. Expired/revoked entries cannot auto-connect; failures leave offline guidance usable.
- Solve the first-download problem with a separately obtainable trusted bundle; hosting updates on a blocked site is insufficient.
- New costs or infrastructure require a product decision. This optional experiment cannot become a silent prerequisite for the primary connection.

5) Scope exclusions

Native Android/iOS applications are deferred at the owner's request. Current
construction targets Windows and Linux; retain responsive browser usability.

No v1 marketplace, public SDK, multi-tenancy, Kubernetes, service-per-module design, complex cryptographic ledger, theme engine, mandatory AI, proprietary client, mass IP/SNI scanner, OS-wide TUN/WinDivert or TLS MITM.
These exclusions do not remove core security, recovery, a polished interface or tested compatibility.
An offline generator can be useful, but it does not create free egress or replace the connection objective.

6) Modular architecture

Use one repository and a modular application. module-map.json owns imports; docs/ARCHITECTURE.md explains boundaries.
contracts: narrow DTOs/ports, capabilities and typed errors, without provider or I/O implementations.
domain: user/policy/expiry/credential state, without provider APIs.
security: admin identity, sessions, recovery and credential verification.
config: structural/semantic/capability validation and revisions.
compiler: deterministic supported client-format output, without database or admin-login calls.
subscriptions: credential-aware delivery and profile references, independent of admin sessions.
protocols: transport-neutral parsing and protocol semantics.
transports: protocol-neutral stream lifecycle, backpressure and cleanup.
providers: local/Cloudflare runtime adapters and actual capabilities.
storage: D1 repository adapters, transactions and migrations.
diagnostics: allowlisted errors and timed observations, not traffic logs.
installer: preflight, inventory, installation, resume, selective removal and optional bootstrap orchestration.
ui: presentation and safe HTTP API client using contracts, without privileged backend imports.
app: composition and HTTP routes with minimal business logic.

Inject clock, randomness, repositories and I/O through small ports; no DI framework.
UI calls the HTTP API wired by app; it does not import app. Pure protocols return typed results; callers map them through a diagnostics port in contracts.
Module separation does not guarantee process/security isolation. Keep boundary and representative end-to-end tests.
Create directories when real implementation arrives, not empty classes to resemble a finished architecture.

7) Cloudflare account integration

Initial choice: official Deploy to Cloudflare with resource/access guidance after runtime and permission prerequisites exist.
The operator authenticates at Cloudflare; the official flow clones/builds/provisions into the operator's accounts. Recheck actual behavior/scopes before use.
Developer alternative: Wrangler with official authentication and explicit resources; credentials remain in the operator's secure environment.
Later custom OAuth uses minimal scopes, exact redirects, state and appropriate PKCE. Verify current public-client/domain requirements; it is not needed for v1.
Manual API tokens are a necessary-case fallback, scoped by resource, privilege and lifetime. No Global API Key or account password.
Panel login differs from Cloudflare account login. The runtime uses its own D1 binding, not an account token on every request.
No deploy button, OAuth client or production credential is created by preparation work.

8) Performance and platform constraints

Quality depends on the user's network, ingress/egress, congestion, client/core version, DNS, configuration and code. Subscription names do not create speed.
Entry IP and egress ProxyIP differ. A shorter route helps only when permitted and reliable.
Evaluate outbound TCP restrictions, including Cloudflare target ranges, and whether a relay is necessary; do not assume all destinations work.
Measure success, setup time, median/p95 latency, throughput, reconnect, CPU/memory and probe overhead under comparable conditions.
One ping or reachable site cannot establish general quality. Record actual target devices and networks.
The prior dated review records 100000 free requests/account/day, 10 ms CPU/request and 128 MB isolate memory. Revalidate these findings before deployment.
Network waiting is not active CPU time; requests, packets and users are different quota units. Pages Functions provide no independent allowance.
No guaranteed speed, latency, capacity or always-free third-party service without evidence.

9) Construction order and completion

ROADMAP.json owns task IDs and acceptance criteria. Preserve P00-P09 IDs for checkpoint continuity.
P00: preparation contracts, tools and truthful evidence; this redesign refreshes that baseline.
P01: pinned strict TypeScript/build/test/lint, narrow contracts, validators, error catalog, deterministic fixture and early feasibility checkpoint.
P02: controlled local parser/stream proof; then permitted free live connection, measured resources and viable egress.
P03: create -> subscription -> import -> connect -> update; second pinned formatter and minimal profile metadata.
P04: production identity/session/recovery, credential separation, measured expiry/revocation and audit bounds.
P05: atomic configuration, safe rollback, encrypted backup/restore and failed-migration recovery.
P06: polished mobile/RTL UI, resumable install, small playground, staged diagnostics, offline guidance and data inventory.
P07: limited beta with declared real device/network coverage and security/recovery fixes.
P08: release integrity, SBOM/licenses, install/update/restore help and measured claims.
P09: evidence-backed fallback/advice and optional bootstrap integration after a stable core.

Prototypes, beta and public releases have different gates. P02/P03 live trials are restricted authenticated experiments, not a public panel before P04/P05.
Lightweight visual exploration can start early; large feature expansion waits for the working critical path.
Aim for bounded tasks with observable outcomes, not rigid time/line/file limits that split inseparable changes.

10) Runtime and external prerequisites

Local preparation uses Node.js 24 and Git, with no npm dependency, account, domain or API key.
P01 adds pinned compiler/build tooling and validates clean installation; preparation checks do not establish TypeScript safety.
Live work needs the operator's free account, official installation access, applicable permission evidence, real free egress, target clients/devices and test networks.
Domains, DNS, WebAuthn RP ID and OAuth registration are not configured; do not buy domains before feasibility requires them.
Use ignored environment/binding secrets and scoped access. Never put secret values in chat, source or public examples.

11) Development, token efficiency and interruption recovery

Read AGENTS.md, STATE.json, the diff and npm run context. Select one observable task, reuse suitable functions/harnesses, and preserve unfinished changes.
Use targeted reads, small fixtures and bounded retries. After two identical failures, change the diagnosis/approach or report a concrete blocker.
Reuse passes only for verified identical relevant inputs and tool versions. The current check command runs checks; it is not an automatic cache validator.
STATE owns progress and resume actions; CONTINUE owns the static guide. One concise evidence file per phase; no transcripts or competing handoff authorities.
Keep detailed temporary logs outside tracked files. Use adequate reasoning for security/protocol/migration decisions; do not claim unmeasured token savings.
Local commits do not back up to GitHub. Preserve the workspace or transfer a checkpoint. No automatic public wip/* pushes; unfinished publication needs explicit authorization.
Before publication: review diff, run gates, scan secrets, check remote head, preserve concurrent work and never force-push. Report remote CI only when observed.
Routine in-scope coding, dependency/tooling work, local checks and reversible corrections proceed without repeated approval. New costs, changed goals, destructive actions and external messages need specific authorization.
On resume, inspect checkpoints and verify prior external operations before retrying; no blind reinstall, reset or cleanup.

12) Verification and evidence

P00: doctor, project/import/secret/language guards, negative guard tests and current input-hashed evidence.
P01+: actual typecheck/build/lint, compiler-backed boundaries, invariants, malformed input and controlled I/O failures.
Connection: actual cores/devices, controlled destinations and network/resource/reconnect observations; mocks do not establish public connectivity.
Security: credential confusion, expiry/revoke, sessions, CSRF, recovery and bounded attempts.
Data: corrupt/wrong-password backups, fresh restore, revocation-safe rollback and failed migrations.
UI/install: novice trials, keyboard/mobile/RTL, interrupted/repeated setup and preservation of unrelated resources.
docs/TESTING.md owns gates. Record commands, versions, hashes, outcomes and who/what observed them. A verifier label alone is not evidence.
Distinguish pass, fail, not_run, unsupported and skipped. Required unrun checks prevent closure.
Agent-reviewed documents are labeled as such, not independent security review. CI reruns automated gates but cannot substitute for permission or human/device observations.

13) Ownership and licensing

The repository is public and restricted-use, not open source. GitHub viewing/forking rights remain; technically preventing public source copying is impossible.
LICENSE permits personal operation by the owner and authorized operators; free end-user access does not grant unrestricted redistribution or competing-service rights.
Authorship, attribution, commit history, provenance and branding clarify rights but do not guarantee enforcement.
Ideas alone do not impose another project's license. Actual code/dependency integration needs compatibility review; do not silently relicense or copy incompatible GPL/AGPL code.
Visibility and LICENSE remain owner decisions. Obfuscation, spyware, mandatory creator access and backdoors are not protection mechanisms.
Authentication protects installations; signatures/hashes support authenticity, not copy prevention. CODEOWNERS alone does not enforce branch protection.
